# Add a /fodo:changelog skill that creates or updates CHANGELOG.md (Keep a Changelog)

## Request
add skill fodo:changelog that create a CHANGELOG.md file is it doesn't exist yet, writes/updates one from git log or git status, asks questions about what info to include - cf https://keepachangelog.com/en/1.1.0/

## Analysis
Net-new skill; nothing in fodo writes a changelog today and this repo has no CHANGELOG.md itself
(57 commits, tags `v0.1.7` to `v0.1.9` exist, `VERSION.md` holds `0.1.14`, `bin/release.sh` bumps
VERSION.md and every `plugins/*/.claude-plugin/plugin.json`, commits, tags and pushes).

Shape, as a prompt-only SKILL.md like `skills/show/SKILL.md` plus a reference file like
`reference/conventions.md`, so the Keep a Changelog rules are not repeated in the prompt:

- **Create mode** (no `CHANGELOG.md` at the repo root): write the Keep a Changelog 1.1.0 skeleton
  (title, intro sentence, `## [Unreleased]`, one `## [x.y.z] - yyyy-mm-dd` per existing tag when
  the user wants history back-filled, comparison links at the bottom when a remote exists).
- **Update mode** (file exists): read it, find the last version heading, take `git log
  <last-tag-or-heading>..HEAD` (released range) and, if asked, `git status` / `git diff` for
  uncommitted work, and sort the entries into the six Keep a Changelog groups: Added, Changed,
  Deprecated, Removed, Fixed, Security. Conventional-commit prefixes map directly
  (`feat` → Added, `fix` → Fixed, `chore`/`docs`/`refactor` → usually dropped or Changed);
  otherwise the skill reads the diff.
- **Questions** (AskUserQuestion, few rounds): back-fill history or start from now; include
  docs/todo bookkeeping and chores or only user-visible changes; date and version for a new
  release section or leave it under Unreleased; whether a fodo `done/` item should be the source
  for an entry's wording (done items have a Result section and a title, often better than commit
  subjects).
- Never commits; `/fodo:commit` (planned item, `2026-10-30.feature.fodo-commit-skill.md`) is the
  one that asks about CHANGELOG.md before committing, so the two skills should agree on the
  file format and `/fodo:commit` can delegate to this skill's rules.

Open questions for `/fodo:plan`:
- Should `bin/release.sh` promote `## [Unreleased]` to `## [<new>] - <date>` when it bumps the
  version? That makes the changelog part of the release, but adds a shell edit to a prompt skill.
- Source priority when both exist: fodo `done/` items vs git commits for the same change.
- Does the plugin's own `plugins/fodo/CHANGELOG.md` make more sense than a root one for a
  marketplace repo with several plugins? (The plugin directory shows per-plugin metadata.)
- Does the skill belong in fodo at all, or in a separate small plugin, since it is not about
  todos? Fodo already owns decisions and gotchas, so "project memory in markdown" is a fit.

Risks: rewriting an existing hand-written changelog; mitigate by only inserting under Unreleased
or a new version heading and never reordering or deleting existing entries.

## Impacted files
- `plugins/fodo/skills/changelog/SKILL.md`: the new skill, create and update modes, the questions.
- `plugins/fodo/reference/changelog.md`: the format reference (sections, heading forms, link
  footer, mapping from commit prefixes and from fodo item types bug/change/feature).
- `plugins/fodo/README.md`: Commands table row and a sentence in the overview.
- `plugins/fodo/.claude-plugin/plugin.json`: add `changelog` keyword, optional.
- `bin/release.sh`: optional Unreleased → version promotion.

## Plan
1. Write `reference/changelog.md` from https://keepachangelog.com/en/1.1.0/ (sections, order,
   Unreleased, yanked, dates ISO, link references) plus the mapping rules.
2. Write `skills/changelog/SKILL.md`: detect create vs update, gather sources (tags, git log range,
   optional git status, optional done/ items), ask the questions, write or insert, show the diff.
3. README row, plugin.json keyword.
4. Decide on and, if agreed, add the release.sh promotion with a bats test in `tests/release.bats`.
5. Try it on this repo (no changelog yet, 3 tags) and on a repo with an existing changelog.

## Acceptance criteria
- In a repo without `CHANGELOG.md`, `/fodo:changelog` creates a valid Keep a Changelog 1.1.0 file
  with an `[Unreleased]` section and, when asked, one section per existing tag.
- In a repo with one, it adds entries under `[Unreleased]` or a new version heading from the
  commits since the last version, grouped into the six standard categories, and never removes or
  reorders existing entries.
- It asks before including chores/bookkeeping and before back-filling history.
- It never runs `git commit` or `git push`.
- README Commands table lists the skill; `bats tests/` passes.
