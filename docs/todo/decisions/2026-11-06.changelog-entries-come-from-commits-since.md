# Changelog entries come from commits since the last version, with wording from the done/ items completed in that range

## Context
Planning /fodo:changelog. This repo's git history is mostly `chore: commit N changed files before release` and `release: set version` commits, so commit subjects alone give a thin changelog. fodo's done/ items carry a title, a type and a Result section for the same work.

## Options considered
- Commits only: predictable, mapped by conventional-commit prefix, but useless on bundled release commits
- Diff-driven: best wording, slowest, most judgement per run
- Commits enriched by done/ items (chosen): commits in range are the skeleton; when a done/ item has `done_at` inside the range, its title and Result wording replace the commit subject; uncommitted work is only read when the user says so

## Decision
Changelog entries come from commits since the last version, with wording from the done/ items completed in that range

## Consequences
`/fodo:changelog` and `/fodo:commit` share one mapping in `plugins/fodo/reference/changelog.md` (commit prefix → group, done item type → group: bug → Fixed, feature → Added, change → Changed). A range with no usable commits and no done/ items yields "nothing to add", never an empty group. Done items are the better source, so keeping their titles and Results precise pays off twice.
