# Add /fodo:cli to put a fodo command on the PATH

## Request
just like you have '/fodo:valet' to set up http://fodo.test server, add a /fodo:path that will link the fodo.sh to a binary path in the $PATH, so we can do "fodo list" in any repo terminal

## Analysis
Net-new capability, modelled on `/fodo:valet` (`skills/valet/SKILL.md` + `scripts/valet.sh`, with
`link` / `status` / `unlink` subcommands and `tests/valet.bats`).

`fodo.sh` already works from any subdirectory (it `cd`s to the git toplevel), so `fodo list`,
`fodo busy --all`, `fodo path 3` etc. need no new behaviour beyond the points below.

Name: `/fodo:cli`, not `/fodo:path`: `fodo.sh path <id>` already exists, so `fodo path 3` must keep resolving item IDs.

See the PRP below for the decisions taken and the full design.

## Impacted files
- `plugins/fodo/scripts/cli.sh` — new: `candidates`, `link <dir>`, `status`, `unlink`; never sudo
- `plugins/fodo/skills/cli/SKILL.md` — new skill (args `[status|unlink|<dir>]`), asks which bin dir
- `plugins/fodo/scripts/fodo.sh` — resolve own path through symlinks; re-point `~/.claude/todo/fodo.sh`; refuse auto-init when run as `fodo`; header wording
- `plugins/fodo/scripts/web.sh` — re-point `~/.claude/todo/fodo.sh` too (as it does for the dashboard)
- `tests/cli.bats` — new tests
- `plugins/fodo/reference/conventions.md`, `plugins/fodo/README.md`, `README.md`, `plugins/fodo/dashboard/faq.md`, `plugins/fodo/PRIVACY.md` — document `/fodo:cli`

## Plan
Follow the PRP's implementation blueprint (Tasks 1–7) and its validation loop. ✅ Tasks 1–7 done (2026-10-28).

## Acceptance criteria
- `/fodo:cli` asks which directory on `$PATH` to use and creates `fodo` there without sudo;
  `/fodo:cli status` shows where it is and what it points to; `/fodo:cli unlink` removes it (and
  only our link).
- In a new terminal, `fodo list` in any repo with `docs/todo/` (also from a subdirectory) prints
  the same as `fodo.sh list`.
- `fodo` with no arguments prints the help.
- `fodo list` (and every other repo command) in a folder without `docs/todo/` prints an error
  pointing to `fodo init` and creates nothing; the skills (`bash …/fodo.sh`) still auto-init.
- After a plugin update the `fodo` command runs the new version without re-running `/fodo:cli`.
- An existing unrelated `fodo` in the chosen dir is never overwritten.
- `bats tests/` passes, including the new `tests/cli.bats`; `shellcheck plugins/fodo/scripts/*.sh` clean.

## PRP

### Goal
A user runs `/fodo:cli` once, picks a directory on their `$PATH`, and from then on can type
`fodo list`, `fodo busy --all`, `fodo show`-style helper commands (`fodo path 3`, `fodo stale`, …)
in any terminal inside any repo. The command always runs the plugin version Claude Code last used,
refuses to create `docs/todo/` by accident, and can be inspected (`status`) and removed (`unlink`).

### Why
- Read the todo state of a repo without opening Claude Code (`fodo list`, `fodo busy --all`).
- Same "set up once, all repos" pattern as `/fodo:valet` / `/fodo:web`.
- Reuses `fodo.sh` as-is: no second CLI to maintain.

### Decisions taken
- Skill name → `/fodo:cli` (user; `path` collides with `fodo.sh path <id>`).
- Bare `fodo` (no args) → print help, unchanged (user, recommended).
- `fodo` in a folder without `docs/todo/` → refuse with a hint to run `fodo init`, only when invoked
  as `fodo` (basename of `$0`); `bash …/fodo.sh` from the skills keeps auto-init (user, recommended).
- Which bin dir → ask each time: the skill runs `cli.sh candidates` and asks with AskUserQuestion;
  `/fodo:cli <dir>` skips the question (user).
- Surviving plugin updates → stable middle link `<bin>/fodo` → `~/.claude/todo/fodo.sh` →
  `<plugin>/scripts/fodo.sh`; `fodo.sh` and `web.sh` re-point the middle link when it exists, like
  `~/.claude/todo/dashboard` (user, recommended).
- Remember the chosen bin path in `~/.claude/todo/cli-bin` (like `claude-bin`) so `status`/`unlink`
  find it (default; nothing else knows where it went).
- Never `sudo`, never edit shell profiles; if the chosen dir is not on `$PATH`, print a hint line
  (default; mirrors valet.sh never running `valet`/`sudo`).
- Out of scope: shell completion, a man page, aliases other than `fodo`.

### Known gotchas & library quirks
- CRITICAL: `refresh_dashboard_link` and `DASH`-style lookups use `dirname "$0"`. Run as `fodo`,
  `$0` is `<bin>/fodo`, so `../dashboard` is wrong. Compute the real script dir once at the top of
  fodo.sh by following symlinks in a loop (relative targets are relative to the link's dir), then
  use it in refresh functions. `usage()` reading `sed … "$0"` already works through symlinks.
- The CLI guard must check `basename "$0"` = `fodo` (the bin link name), not the resolved path;
  the middle link is named `fodo.sh`, so skills and `bash ~/.claude/todo/fodo.sh` stay unaffected.
- Guard exemptions: `init`, `help`/`-h`/`--help`/empty, `repos`, `busy --all`/`-a`. Put the guard
  in the dispatch section before the `case`, after `ROOT`/`cd` are set. Message (stderr, exit 1):
  `no docs/todo/ in <toplevel or pwd>; run 'fodo init' (or /fodo:init in Claude Code) first`.
- `set -euo pipefail` everywhere; every refresh helper must `return 0` (they run on every command).
- Collision rule (from valet.sh): if `<dir>/fodo` exists and is not a symlink to the stable path,
  die `"<dir>/fodo already exists and was not made by fodo; not touching it"`.
- `candidates`: iterate `$PATH` entries in order, dedupe, skip non-existent/non-writable and
  relative entries; mark `~/.local/bin` and `~/bin` first if present. Output one dir per line
  (prefix `* ` for the recommended first one is fine but keep it parseable — plain paths are simplest).
  If none is writable, print nothing and exit 0; the skill then offers `~/.local/bin` (created by
  `link`, with the PATH hint).
- `link <dir>`: dir required (exit 1 with usage otherwise); `mkdir -p` it only when it is under
  `$HOME`; must be an absolute path. After linking, if `<dir>` is not on `$PATH` print
  `path: <dir> is not on your PATH; add  export PATH="<dir>:$PATH"  to your shell profile`.
  If another `fodo` is earlier on PATH (`command -v fodo` ≠ `<dir>/fodo`), print
  `shadowed: <other> comes first on your PATH`.
- Re-linking to a different dir: remove the old `<cli-bin>` link first if it is ours.
- Tests run on macOS bash 3.2: no `mapfile`, no `${var,,}`, no `readlink -f`.

### Deviations from the spec
- `cli.sh` with no arguments runs `status`; the skill does the asking, so a bare script call changes nothing.
- `cli.sh link` creates a missing directory only under `$HOME`, and refuses relative or non-writable directories (the PRP only said "mkdir -p under $HOME").
- The help text still shows commands as `fodo.sh <command>`, also when run as `fodo`; left as is.

### Discoveries
- `tests/web.bats` "faq covers every command" requires a `### /fodo:<skill>` section and a `(#fodo-<skill>)` link in faq.md for every skill; new skills must update faq.md.
- `refresh_dashboard_link` used `dirname "$0"`, which would have pointed the Valet dashboard link at `<bin>/../dashboard` when run through a symlink; fixed with the `SELF_DIR` resolution.
- `usage()` prints lines 5–23 of the script; header edits must keep that range in sync.
- The plugin cache keeps `fodo.sh`'s exec bit (100755 in git), which the `fodo` symlink relies on. `valet.sh` is 100644 (harmless, it is always run with `bash`).
- Possible follow-up: have `usage()` print `fodo` instead of `fodo.sh` when run as `fodo`.
