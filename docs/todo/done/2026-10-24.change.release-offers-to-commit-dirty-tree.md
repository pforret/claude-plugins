# Let release.sh offer to commit uncommitted work

## Request
let @bin/release.sh check for uncommitted work, and propose to commit it : default message is a list of all changed files, but user can override git commit messagge

## Analysis
A change to existing behaviour: `bin/release.sh:51` currently dies with "working tree not clean; commit or
stash first" when `git status --porcelain` is non-empty. Instead it lists the changed files and offers to
commit them (all of them, untracked included) as a separate commit before the release commit, with a
default message listing every changed file that the user can accept with Enter or replace. The open
points from the first analysis were settled during planning; see `### Decisions taken` in the PRP.

## Impacted files
- `bin/release.sh` — argument parsing (`--commit`, `-m/--message`), header/usage, dirty-tree handling
- `tests/release.bats` — make the dirty-tree refusal explicit about stdin; add tests for the new flags and dry run
- `docs/publishing.md` — describe the new step in the release checklist

## Plan
See `### Implementation blueprint` in the PRP below.

## Acceptance criteria
- With a dirty tree and a TTY, `bin/release.sh` lists the changed files and prompts: Enter commits with the
  default message, typed text commits with that text as the full message, `n`/`no` aborts without changes.
- The default message is `chore: commit <N> changed files before release` plus one `- <path>` line per file
  (renames as `old -> new`, deletions included).
- `--commit` commits with the default message and `-m <msg>` / `--message <msg>` / `--message=<msg>` with
  `<msg>`, both without prompting.
- Without a TTY and without either flag, a dirty tree is refused as today ("not clean").
- `--dry-run` never prompts or commits; it reports that it would commit N files.
- The work commit is made after all refusal checks and before the release checks, and is pushed together
  with the release commit and tag; if a check fails the script says the work commit is local and unpushed.
- `shellcheck bin/*.sh` is clean and `bats tests/release.bats` passes.

## PRP

### Goal
`bin/release.sh` no longer refuses a dirty tree outright: it shows what changed and proposes a commit
(default message = file list, user may override), then releases as before. Non-interactive runs commit
only when told to with `--commit` or `-m`.

### Why
- The usual flow is "finish work, release"; today that needs a manual `git add -A && git commit` (or
  `setver auto`) first, and forgetting it ends in a refusal.
- Keeps the release a single command while still never committing anything unasked.
- Flags keep it scriptable and testable in bats.

### Decisions taken
- No TTY behaviour → add `--commit` (default message) and `-m/--message <msg>` (custom message); without a
  TTY and without a flag, refuse as today (user)
- What to stage → everything incl. untracked: `git add -A`; the list is shown first (user)
- Default message → subject `chore: commit N changed files before release` + body with one `- path` per
  line, renames `old -> new` (user)
- Order → work commit before the release checks; on check failure it stays local and unpushed (user)
- Prompt answers → empty = default, `n`/`no` (case-insensitive) = abort, anything else = full message
  that replaces subject and body (default, matches "user can override the message")
- Where the decision is taken → at the dirty-tree check (line 51), so the user answers before the fetch;
  the commit itself happens after the dry-run exit and before the checks, so a later refusal
  (tag exists, behind origin) never leaves a stray commit (default)
- `--dry-run` with a dirty tree → print `would commit N changed files` and continue the dry run, no prompt
  (default; today a dry run on a dirty tree dies, this is more useful)
- TTY detection → `[[ -t 0 ]]`, prompt with `read -r -p` from stdin (default)

### Known gotchas & library quirks
- bats does not guarantee stdin is a non-TTY when run from a terminal: in tests feed `< /dev/null` to every
  run that hits the dirty-tree path, so the no-TTY branch is exercised deterministically.
- Porcelain output for a rename staged in the index is `R  old -> new`; for unstaged untracked dirs, git
  lists `?? dir/` unless `-uall`; use `--untracked-files=all` so every file is named.
- `git commit -m "$subject" -m "$body"` produces subject + blank line + body; a custom message is passed
  as a single `-m "$msg"`.
- `shellcheck` runs on `bin/*.sh` in the release checks itself, so the script must stay clean.
- Header comment and `usage()` share lines: keep the header the usage text.

  (body has `- notes.txt`, `- untracked.txt`, `- old.txt -> renamed.txt`; origin main == HEAD, tag v0.1.1 on origin).
- `--commit`, `-m <msg>`, `--message=<msg>` without prompt: bats "--commit …" and "-m and --message= override the commit message" → ok.
- No TTY + no flag refuses with "not clean" and names `--commit`: bats "refuses a dirty tree, …" (with `< /dev/null`) → ok.
- `--dry-run` reports and changes nothing: bats "dry run with a dirty tree reports and changes nothing" → ok.
- Work commit precedes the release commit, pushed together; failure message when a check fails: bats tests 7 and
  "a failing check after the work commit says it is not pushed" → ok.
- `shellcheck bin/*.sh` → clean; `bash -n bin/release.sh` → ok; `bash bin/release.sh --help` shows `[--commit | -m <msg>]`.
- `bats tests/release.bats` → 11 ok, 0 not ok; `bats tests/` → 51 ok, 0 not ok.
- `docs/publishing.md` documents `--commit`, `-m "message"` and the prompt (lines 12–20).

### Deviations from the spec
- "Not pushed" warning: an EXIT trap set right after the work commit and cleared with `trap - EXIT` after the push,
  instead of a `work_committed` flag + ERR trap (shellcheck SC2034 flagged the flag; the trap alone is simpler).
- File lists printed with a `while IFS= read -r` loop instead of `sed 's/^/…/'` (shellcheck SC2001).
- The "failing check" test triggers the failure via shellcheck (the temp repo has no `plugins/*/scripts/*.sh`)
  rather than via a failing bats file.

### Discoveries
- The PRP pseudocode for `-m` used `$1` in the error message after `shift`, which is empty there; replaced with a
  literal "-m / --message needs a message".
- When the prompt reads EOF (e.g. input piped straight into `script`), `read` fails and the answer defaults to
  `n` → abort. That is the safe outcome, and it is why the manual check needs a delayed input.
- The prompt itself is still not covered by bats (needs a pseudo-terminal; `script` flags differ between macOS and Linux).
