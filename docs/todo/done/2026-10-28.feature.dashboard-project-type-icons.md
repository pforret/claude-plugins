# Show project type icons (PHP, Node, Python, Bash, Java, …) on the dashboard

## Request
the web interface currently only distinguishes Laravel projects with an icon plugins/fodo/dashboard/laravel.svg
support more type of projects like: PHP, Node, Python, Bash, Java, ...
put the icons in a subfolder

## Analysis
Net-new capability in the dashboard. Today `index.php:1031` sets a boolean `'laravel' => is_file($real . '/artisan')`
per repo block, and three places render `laravel.svg` when it is true: the overview card (`render_card`,
`index.php:908`), the repo detail header (`index.php:1304`) and the busy-all list (`index.php:1349`).
`style.css` sizes `img.laravel` in three rules (lines 117, 171, 181).

The change replaces the boolean with a detected project type (or list of types), decided by marker files in the
repo root, for example:
- Laravel: `artisan` (checked before plain PHP, since Laravel is also PHP)
- PHP: `composer.json`
- Node: `package.json`
- Python: `pyproject.toml`, `requirements.txt`, `setup.py`, `Pipfile`
- Java: `pom.xml`, `build.gradle(.kts)`
- Bash: `*.sh` scripts in the root or a `bashew`-style layout with no other marker
- possibly Go (`go.mod`), Rust (`Cargo.toml`), Ruby (`Gemfile`)

Icons move to a subfolder, e.g. `plugins/fodo/dashboard/icons/<type>.svg` (`laravel.svg` moves there).

Open questions (for `/fodo:plan`):
- One icon (most specific type wins) or several icons for polyglot repos (e.g. PHP + Node in a Laravel app)?
- Icon source and license: hand-drawn simple SVGs vs. a set like Simple Icons (CC0); PRIVACY/README note if external.
- Does the Valet setup or the built-in server need anything to serve a subfolder? (Static files from `dashboard/`
  should just work; check the PHP router in `index.php` for `?icon=` style routing that might intercept paths.)
- Detection cost: only `is_file` checks per repo on each request; keep it cheap (no recursive scans).

## Impacted files
- `plugins/fodo/dashboard/index.php` — detect the project type(s) per repo; render the matching icon in the three places
- `plugins/fodo/dashboard/style.css` — generalise the `img.laravel` rules to a shared class (e.g. `img.ptype`)
- `plugins/fodo/dashboard/laravel.svg` — move to `icons/laravel.svg`
- `plugins/fodo/dashboard/icons/` — new SVGs: php, node, python, bash, java (and any extras)
- `plugins/fodo/dashboard/faq.md` — mention the project type icons and how they are detected
- `tests/web.bats` — fixtures and assertions for detection, single-icon priority and the icon files being served

## Plan
See the PRP below (Approach and Validation loop).

## Acceptance criteria
- A Laravel repo still shows the Laravel icon, now loaded from `icons/laravel.svg`; no SVG is left in the `dashboard/` root except `icon.svg`.
- Repos with `composer.json`, `package.json`, Python, Java or Bash markers show the matching icon on the overview card, the detail header and the busy-all list.
- Repos with no known marker show no type icon and no broken image.
- Each icon has an `alt` and a `title` naming the type.
- Icons stay legible in Light/Dark Colors and Monochrome schemes.
- Works under both `/fodo:web` and `/fodo:valet`.

## PRP

### Goal
Every repo on the dashboard shows at most one project-type icon, picked from marker files in the repo root by a
fixed priority (Laravel > PHP > Node > Python > Java > Go > Rust > Ruby > Bash), in the three places that show the
Laravel icon today. All type icons, `laravel.svg` included, live in `plugins/fodo/dashboard/icons/`. Repos without
a known marker show nothing.

### Why
- At a glance the overview tells which stack a repo is; today only Laravel repos get that.
- Reuses the existing per-repo block and the existing icon slots; no new pages or config.
- Purely local and cheap: a handful of `is_file`/`glob` calls per repo per request, no network.

### Decisions taken
- How many icons per repo? → Most specific only, one icon by priority order (user) (recorded: decisions/2026-10-29.the-dashboard-shows-one-project-type.md)
- Icon source? → Simple Icons brand marks (CC0), committed as files, filled with each brand's hex (user) (recorded: decisions/2026-10-29.project-type-icons-come-from-simple.md)
- Which types? → Core set Laravel, PHP, Node, Python, Java, Bash plus Go, Rust, Ruby; no Docker (user) (recorded: decisions/2026-10-29.the-dashboard-detects-laravel-php-node.md)
- How to recognise Bash? → a `*.sh` file in the repo root or in `bin/`, only when no other type matched (user) (recorded: decisions/2026-10-29.a-repo-counts-as-bash-when.md)
- Java icon → Simple Icons has no Java/Oracle mark (removed at the brand's request); use `openjdk` (default)
- Keep the existing `laravel.svg` artwork, just move it (default)
- Folder/file/class names → `dashboard/icons/<type>.svg` named by type key (laravel, php, node, python, java, go, rust, ruby, bash), not by Simple Icons slug; CSS class `ptype` (default)

### Known gotchas & guardrails
- Mirror the existing patterns named under Context; do not introduce new ones for this item
- CRITICAL: no external requests from the dashboard (`tests/web.bats` "dashboard makes no external requests"); download the SVGs at implementation time and commit them, never link a CDN.
- CRITICAL: `rust` (#000000) and possibly `openjdk` are dark marks that vanish on the dark schemes; give them a CSS rule under the dark scheme selectors (e.g. `filter:invert(1)`), or pick a lighter fill. Check all four schemes.
- PRESERVE: `icon.svg` stays in `dashboard/` (it is the fodo logo/favicon, linked from `<head>` and render_agent_row); only type icons move to `icons/`.
- PRESERVE: the overview and busy list keep their current sizes (16 / 18 detail / 14 busy list); only the class name changes.
- Use `git mv` for `laravel.svg` so history follows it.
- Paths are relative (`icons/php.svg`, no leading slash), like the existing `laravel.svg` reference; works under both `php -S -t dashboard` (/fodo:web) and the Valet symlink.
- Detection is root-only plus `bin/*.sh`; no recursive scans (runs on every page load for every repo, plus the minute auto-reload).
- Laravel must be checked before PHP (Laravel apps have composer.json) and Node after PHP (Laravel apps have package.json).
- Escape nothing user-supplied into the icon markup except via e(); the type key comes from your own table, not from the repo.

### Approach
In `index.php`, next to `find_favicon()`, add a `project_type(string $repo): ?array` that walks an ordered table
`type => [label, markers…]` (markers are root-relative files; Bash uses `glob('*.sh')` in root and `bin/`) and returns
the first match with the type, label and the marker found. Store it in the block as `'ptype'` instead of `'laravel'`.
Add a small `render_ptype(?array $t, int $size): string` that returns
`<img class="ptype" src="icons/<type>.svg" alt="<Label>" title="<Label> project (<marker> found)" width=… height=…>`
or `''`, and use it in the three render sites (keep the leading space where it exists now). In `style.css`, rename the
three `img.laravel` rules to `img.ptype` and add the dark-scheme rule for dark marks. Add the SVGs under `icons/`
(laravel moved, eight new). Add one FAQ paragraph (where the dashboard overview is described) listing the types and
markers. Add tests to `tests/web.bats`.

```bash
#   - repo with only bin/run.sh → 'icons/bash.svg'; repo with go.mod → 'icons/go.svg'

                                   # each icon visible (rust/openjdk too), sizes 16/18/14 as before, no broken images
```
