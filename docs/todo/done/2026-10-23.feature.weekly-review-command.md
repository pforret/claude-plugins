# Add /fodo:review weekly review command

## Request
GTD-inspired: `/fodo:review` (the weekly review). Claude goes through the items and flags planned items
older than N days, busy items whose files haven't changed in git for a while, and PRPs whose code has
moved on since they were written. For each one it asks you to keep, re-plan, park, skip or start.

## Analysis
GTD's "Review" step has no counterpart in fodo; items go stale silently. Claude can check each item
against the actual code (git log on the `files:` frontmatter), which a plain todo app cannot.
The someday stage (park) and the wait marker already exist, so every action maps onto an existing
`fodo.sh` move. The only helper gaps are a `stale` report and allowing plan → planned (re-plan).

## Impacted files
- `plugins/fodo/skills/review/SKILL.md`: new skill with the review walk-through
- `plugins/fodo/scripts/fodo.sh`: new `stale` subcommand; `move-file … planned` also accepted from `plan/`
- `plugins/fodo/skills/plan/SKILL.md`: replace an existing `## PRP` instead of appending a second one
- `plugins/fodo/reference/conventions.md`: review, `reviewed:` field, plan → planned
- `plugins/fodo/README.md`, `README.md`: command tables
- `plugins/fodo/dashboard/faq.md`: `### /fodo:review` section + link (enforced by `tests/web.bats`)
- `tests/fodo.bats`: tests for `stale` and plan → planned

## Acceptance criteria
- `fodo.sh stale [--planned <days>] [--busy <days>]` prints a table of stale planned, plan and busy
  items with the reason each was flagged, or `_Nothing stale._`
- `/fodo:review [planned-days [busy-days]]` walks every flagged item and asks what to do with it
- Keep sets `reviewed: <today>`; park, skip and re-plan of a P item run immediately via `fodo.sh`;
  plan/start/finish are listed as follow-up commands with the IDs valid after all moves
- `fodo.sh move-file <plan item> planned` works; `/fodo:plan` on such an item replaces its old PRP
- README (both), conventions and FAQ list `/fodo:review`; `bats tests/` and `shellcheck` pass

## PRP

### Goal
A new `/fodo:review` skill (GTD weekly review) plus a `fodo.sh stale` helper command. The helper
flags, per repo:
- **planned** items whose age exceeds `--planned` days (default 30); age counts from the later of
  `reviewed:` and `created:` (fallback: the filename date);
- **busy** items with no activity for more than `--busy` days (default 14); last activity = latest of
  the last git commit touching any `files:` path, `busy_at:` and `reviewed:`;
- **plan** items whose `files:` paths have git commits after the later of `plan_at:` and `reviewed:`
  (the PRP's code has moved on).

The skill runs the helper, asks per flagged item what to do, executes the quick actions immediately
and ends with a list of follow-up commands (`/fodo:plan 3`, `/fodo:start P1`, `/fodo:done B2`).

### Why
- Items go stale silently; GTD's weekly review is the missing step in fodo's lifecycle.
- Uses the `files:` frontmatter that `/fodo:add` and `/fodo:plan` already maintain, so staleness is
  measured against the real code, not only dates.
- Reuses existing moves (someday, skipped, set) so indexes stay consistent.

### Decisions taken
- Thresholds → planned 30 days, busy 14 days, plan = any commit to `files:` after `plan_at`;
  overridable per run: `/fodo:review [planned [busy]]` → `fodo.sh stale --planned N --busy M` (user)
- Bookkeeping → "Keep" sets `reviewed: <today>` in the item frontmatter, which restarts its age
  clock; no repo-level `.last_review` file (user)
- Re-plan and start → queued as follow-up commands printed at the end, never run inline. Keep, park
  and skip run immediately. Re-planning a P item moves it back to planned now (helper must allow
  plan → planned) and `/fodo:plan` replaces an existing `## PRP` instead of appending a second (user)
- Dashboard → no staleness badge in this item; CLI only (user). Could be a separate todo later.
- Waiting busy items → still checked; the reason column appends `waiting on: <reason>` (default)
- Options per stage (AskUserQuestion allows max 4, plus the automatic "Other"):
  planned: Keep · Plan/Start (follow-up `/fodo:plan` if size is medium/large/unknown, else
  `/fodo:start`) · Park · Skip; plan: Keep · Re-plan · Start · Park (Skip via "Other: skip <reason>");
  busy: Keep · Finish (follow-up `/fodo:done B<n>`) · Wait (ask reason, `fodo.sh wait`) · Skip (default)
- Output format of `stale` → markdown table like the other indexes so Claude can show it verbatim (default)

### Known gotchas & library quirks
- CRITICAL: macOS `date` is BSD. Convert `YYYY-MM-DD` to epoch portably:
  `date -j -f %Y-%m-%d "$d" +%s 2>/dev/null || date -d "$d" +%s` (BSD first, GNU fallback). Days =
  `(today_epoch - d_epoch) / 86400`; compute today the same way from `date +%Y-%m-%d` so the time of
  day cancels out. Skip (don't crash) when a date is empty or unparsable: `set -euo pipefail` is on.
- `field` only reads scalar keys. `files:` is a YAML list; parse it with awk inside the first
  frontmatter block: after a line `files:`, take lines matching `^[[:space:]]*-[[:space:]]+`,
  strip the dash, surrounding quotes and backticks; stop at the first line that is not a list item.
- Comparing dates: `YYYY-MM-DD` strings compare correctly with `[[ "$a" > "$b" ]]`; use that to take
  the max of created/reviewed/plan_at/busy_at instead of converting.
- `git log` must run from the repo root (fodo.sh already cd's there for relative ROOT). With an
  absolute TODO_ROOT outside a repo, `git log` fails: guard with `git rev-parse --is-inside-work-tree`
  and treat "no git" as "no commits" (busy falls back to dates, plan items are never flagged).
- Only `files:` paths are checked, not the item file itself (moving the item is a commit to it).
- A plan item without `plan_at:` (hand-made) uses `created:`.
- IDs shift after every move. The review skill must hold items by **path** while acting, and compute
  the IDs in the follow-up commands only after all moves, from `fodo.sh list`.
- `set_field` inserts new keys right after `status:`; `reviewed:` therefore lands there. Fine.
- Waiting busy items must keep `waiting_on`; "Keep" only sets `reviewed:`.
- `usage()` is `sed -n '5,19p'`: adding a header line for `stale` means bumping it to `5,20p`
  (check `fodo.sh help` output afterwards; the "unknown command exits 1, help exits 0" test exists).
- shellcheck runs on all scripts; quote everything, use `local`.
