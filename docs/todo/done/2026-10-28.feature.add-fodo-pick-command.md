# Add an interactive fodo pick command

## Request
create a 'fodo.sh pick', which lists all backlog & planned tasks (with fzf if available, otherwise show a list and let the user enter a number) , and when selected: for a backlog the choice is given between 'fodo plan' or 'fodo start' of the item, for a planned item, it is started

## Analysis
(Superseded where it differs by the PRP's Decisions taken below.) Net-new interactive subcommand of `fodo.sh`, aimed at terminal use through the `fodo` command from
`/fodo:cli`. "Backlog" = the planned table (`docs/todo/*.md`, IDs `1, 2, …`); "planned" = the plan
table (`docs/todo/plan/`, IDs `P1, P2, …`).

The item data is already there: `item_files`, `field <file> title`, and the ID scheme used by
`write_index` / `resolve` (`plugins/fodo/scripts/fodo.sh`). `pick` builds rows like
`3  feature  medium  Fix login redirect` and `P1 feature  medium  9/10  Add /fodo:cli …`.

- **Selection**: `fzf` when `command -v fzf` succeeds and stdin/stdout are a terminal; otherwise
  print a numbered list and `read` a number (empty or `q` = cancel). Needs a TTY: when not
  interactive, refuse with a clear message (or print the list only).
- **Action**: planning and starting are Claude Code skills (`/fodo:plan`, `/fodo:start`), not
  shell commands. `fodo.sh` cannot run them itself, so `pick` has to either launch
  `claude "/fodo:plan 3"` / `claude "/fodo:start P1"` (interactive Claude Code session with that
  prompt, in the repo root), or print the command to paste. Backlog item → ask plan or start
  (second fzf/`read` prompt); plan item → start directly.
- Launching `claude` from a helper the skills also run is new: the skills never call `pick`, but the
  command must not hang or launch anything when run non-interactively (tests, hooks).
- The CLI guard from `/fodo:cli` (no auto-init when run as `fodo`) already covers `pick`.

Open questions for `/fodo:plan`:
- Launch `claude` directly (`exec claude "/fodo:start P1"`) or print the command? Option to
  `--print`? What if `claude` is not on the PATH (print instead)?
- Include busy items (resume) or waiting items? Request says backlog + planned only.
- Quick items (`size: unknown`) in the backlog: same plan/start choice?
- fzf preview pane with the item file (`--preview 'sed -n 1,40p {file}'`)?

## Acceptance criteria
- `fodo pick` lists backlog (`1…`), plan (`P1…`) and busy (`B1…`) items; with fzf and a terminal it
  uses fzf with an item preview, otherwise a numbered list and a number prompt read from stdin.
  Empty input, `q` or fzf Esc cancels with exit 0 and no action.
- Picking a backlog item asks plan or start → `/fodo:plan <n>` or `/fodo:start <n>`.
- Picking a plan item → `/fodo:start P<n>`; picking a busy item → `/fodo:start B<n>`; no further question.
- With `claude` on the PATH and a terminal, it runs `claude "/fodo:<cmd> <id>"` (interactive session)
  from the repo root, after printing what it runs. Otherwise it prints
  `Run in Claude Code: /fodo:<cmd> <id>` and exits 0.
- No backlog, plan or busy items → a message, exit 0. Piped/empty stdin never hangs.
- `shellcheck plugins/fodo/scripts/*.sh` clean; `bats tests/` passes with the new tests.

## PRP

### Goal
`fodo pick` in a terminal shows the backlog, plan and busy items of the current repo, lets the user
choose one (fzf with a preview when available, else a numbered prompt), decides the matching fodo
skill (`/fodo:plan` or `/fodo:start` for backlog, `/fodo:start` for plan and busy items) and opens an
interactive Claude Code session that runs it. Without `claude` or a terminal it prints the command.

### Why
- One keystroke path from "what's next?" to working on it, outside Claude Code (via `/fodo:cli`).
- Planning and starting are skills, not shell code, so the shell can only hand off to Claude.
- Reuses the table IDs (`n`, `P<n>`, `B<n>`) that every skill already accepts.

### Decisions taken
- How to launch Claude → interactive `claude "/fodo:<cmd> <id>"`, not `claude -p` (user: `-p` is headless, so `/fodo:plan` could not ask its questions and `/fodo:start` would run unattended; the session gets the command as its first prompt and the user sees it run). (recorded: decisions/2026-10-28.fodo-pick-launches-an-interactive-claude.md)
- Busy items → included; picking `B<n>` runs `/fodo:start B<n>` (resumes waiting items) (user). (recorded: decisions/2026-10-28.fodo-pick-also-lists-busy-items.md)
- fzf preview → yes, the item file's first lines (user, recommended). (recorded: decisions/2026-10-28.fodo-pick-shows-an-fzf-preview.md)
- No `claude` on PATH or no terminal → print `Run in Claude Code: /fodo:<cmd> <id>`, exit 0 (user, recommended). (recorded: decisions/2026-10-28.fodo-pick-prints-the-claude-command.md)
- Quick items (`size: unknown`) in the backlog → same plan/start choice; the skills fill them in (default).
- Someday, done and skipped items → not listed (default; request scope).
- Backlog question → second chooser with two entries `plan` / `start` (fzf) or `[p]lan or [s]tart?` (fallback); an empty answer cancels, like the first prompt (default).

### Known gotchas & guardrails
- Mirror the existing patterns named under Context; do not introduce new ones for this item
- macOS bash 3.2: no `mapfile`, no `read -e -i`, no associative arrays; keep rows in a newline string.
- Rows must carry the file path for the preview but show only ID/type/size/extra/title: use a tab
  delimiter and `fzf --delimiter '\t' --with-nth 1..-2 --preview 'sed -n 1,60p {-1}'` (path last);
  keep the path relative (fodo.sh has already cd'd to the repo root).
- Use fzf only when `command -v fzf` and `[ -t 0 ] && [ -t 1 ]`; otherwise the numbered fallback
  reads from stdin with `read -r` (EOF → cancel), so `printf '2\n' | fodo pick` works and tests never hang.
- Launch only when `command -v claude` and `[ -t 0 ] && [ -t 1 ]`; print `Running /fodo:start P1 in Claude Code…`
  then `exec claude "/fodo:start P1"`. Never pass `-p`. In tests stdout is not a terminal → printed command.
- The numbered list and prompts go to stdout like `list`; the final printed line must be exactly
  `Run in Claude Code: /fodo:<cmd> <id>` so tests can match it.
- `set -euo pipefail`: fzf exits 1/130 on cancel — guard with `|| true` / `|| return 0`.
- PRESERVE: every existing command's output and the CLI guard (pick stays guarded: no docs/todo/ → error).
- Also update: header Commands list in fodo.sh, conventions.md helper block (`fodo.sh pick`) and `/fodo:cli`
  paragraph, plugins/fodo/README.md + README.md + faq.md `/fodo:cli` text (`fodo pick`).

### Approach
All in `plugins/fodo/scripts/fodo.sh`: a `pick_rows` helper that emits one tab-separated row per
backlog, plan and busy item in table order (ID, type, size, then confidence `n/10` for plan or
`⏸ reason` for waiting busy items, title, relative path), reusing `item_files`/`field` and the title
fallback of `write_index`; a `pick` function that exits with "nothing to pick" when there are no
rows, chooses a row via fzf (with preview) or the numbered fallback, maps the ID to the skill (plain
number → second plan/start prompt; `P`/`B` → start), and hands off via `exec claude "<cmd>"` or the
printed line. Add `pick` to the dispatch and the header. Tests in `tests/fodo.bats` drive the
fallback with piped stdin and a stub `claude` that writes a marker file (must stay absent). Then the
doc touches listed above.

## Notes
- Deviation: the numbered list and the prompts go to **stderr**, not stdout as the PRP said. `pick_one` runs inside `$(…)`, so stdout is captured; the last stdout line is still exactly `Run in Claude Code: …` / `cancelled` / `nothing to pick…`.
- Discovery: inside `$(…)`, `[ -t 1 ]` is always false, so the terminal check (`tty`, `PICK_FZF`) is computed once in `pick`, before any command substitution.
- Discovery: with a piped answer, `read` prints no newline, so an `echo >&2` follows only when stdin is not a terminal.
- Discovery: `fzf --with-nth 1..-2` also hides the path from search, and the selected line still comes back whole (path included), so the preview's `{-1}` and the row parsing work.
- Note: `~/.local/bin/fodo` currently runs the 0.1.12 cache, which has no `pick`; the new command shows up after the next release + `/plugin marketplace update`, or with `--plugin-dir`.
