# Find and fix the flaky dashboard bats test

## Request
Possibly flaky dashboard test: `bats tests/` once gave 53/54 without showing which test failed. Reruns were clean. (Follow-up from the two-minute-rule item's Discoveries.)

## Analysis
Seen once, on 2026-10-25, when `bats tests/` ran twice back to back in one shell command: the second run counted 53 "ok" of 54, and the
failing line was not captured. Every single run before and after was 54/54. Likely suspects in `tests/web.bats`:
- `TODO_WEB_PORT=$((20000 + RANDOM % 20000))` in `setup()`: a port still in TIME_WAIT or used by another process
  makes `php -S` fail to bind.
- `plugins/fodo/scripts/web.sh:53` waits with `curl --retry 10 --retry-connrefused --retry-delay 1`, but a test that
  calls `curl` right after might hit a server that is slow to serve its first request.
- `teardown()` stops the server, but a kill that doesn't finish before the next test's `start` could make
  "already running" / pidfile assertions race.
The cause is not known yet, so step 1 is to reproduce it.

## Impacted files
- `tests/web.bats`: probably the port choice or a readiness wait
- `plugins/fodo/scripts/web.sh`: maybe, if start/stop need to wait for the port to be free or closed

## Plan
1. Reproduce: `for i in $(seq 1 20); do bats tests/web.bats | grep '^not ok' ; done`, also under load (run two loops at once).
   Capture the failing test name and its output.
2. Fix the root cause (e.g. pick a free port by trying to bind first, wait for the stop to complete, or retry the bind
   in `web.sh`). Don't just add sleeps or retries in the test.
3. Rerun the loop until 20/20 runs are clean.

## Acceptance criteria
- The failing test is identified and its cause written down in the item
- 20 consecutive `bats tests/web.bats` runs (and two parallel loops) give no `not ok`
- `bats tests/` and `shellcheck plugins/fodo/scripts/*.sh` pass

## Notes
- [x] 1. Reproduce: **not reproduced.** 20 sequential `bats tests/web.bats` runs → 0 failures (~25 s per run).
  3 parallel loops × 5 full `bats tests/` runs → 0 failures. No miscounted `ok` lines (all logs: `^ok` count equals the plan).
  `stop` race probe (start → stop → curl at once, 100 cycles) → 0/100 got a 200, so the `stop` test is not the cause.
- [x] 2. Real bug found while checking the port-collision suspect: `web.sh start` on a port another server already
  answers on printed `running: …` and exited 0, although its own php failed (`Failed to listen … Address already in use`).
  The readiness curl got the *other* server's reply, and `status` then said "not running". In web.bats a random
  `TODO_WEB_PORT` collision would make a test talk to a foreign dashboard (other registry, other fixtures): this is the most
  plausible cause of the single 53/54, but it's unproven.
  Fix in `plugins/fodo/scripts/web.sh`: (a) before starting, refuse with
  "port N is already in use by another process; pass another port" when something answers; (b) after the readiness curl,
  also require that our own pid is still alive (`running_pid`), so a bind lost in the meantime fails with the log tail.
  New test "start refuses a port another server already answers on" fails without the fix (`not ok 8`), passes with it.
- [x] 3. `shellcheck` clean · `bats tests/` → 56/56, exit 0 · 10 more `web.bats` runs after the fix → 0/10 failed.
- Deviation: acceptance asks for "the failing test identified". It wasn't: the flake never recurred in 35+ runs. The fix
  targets the one mechanism that is shown (by a manual repro) to make tests pass/fail by chance. Collisions now fail
  loudly with a clear message instead of silently.
- Discovery: `web.bats` is slow (~25 s for 19 tests), mostly from server start/stop per test.

## Result

### Verification
- "Failing test identified": **not met.** The flake never recurred: 20 sequential `bats tests/web.bats` runs and
  3 parallel loops × 5 `bats tests/` runs gave 0 failures, and no log had a miscounted `ok` line. The user accepted closing on that basis.
- `stop` race ruled out: 100 start → stop → curl cycles → 0/100 got a 200
- Port collision reproduced by hand before the fix (second `web.sh 42777` printed `running:` and exited 0 while its php
  logged `Address already in use`). After the fix: `port 42778 is already in use by another process…`, exit 1
- New test "start refuses a port another server already answers on" → `not ok 8` with the fix stashed, ok with it
- 10 `bats tests/web.bats` runs after the fix → 0/10 failed
- `bats tests/` → 56/56, exit 0 · `shellcheck plugins/fodo/scripts/*.sh` → clean

### Deviations from the spec
- The root cause of the original 53/54 was not proven. Instead, a real start-up bug that makes web tests pass or fail by
  chance (silent port collision) was fixed and covered by a test, so any recurrence now fails loudly with a clear message.

### Discoveries
- `web.sh start` used to report success when another process held the port, and served nothing of its own. That also
  affects real users: `/fodo:web` could open the browser on a different app or an old dashboard.
- `web.bats` takes ~25 s for 19 tests, mostly per-test server start/stop.
- Bats 0.4.0 locally (no `-f`); single tests can't be selected.

### Changes
- plugins/fodo/scripts/web.sh: refuse a port that already answers; require our own pid alive after the readiness check
- tests/web.bats: new test "start refuses a port another server already answers on"
- no commits
