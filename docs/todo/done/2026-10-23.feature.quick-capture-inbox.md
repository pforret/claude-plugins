# Add quick capture mode to /fodo:add

## Request
GTD-inspired: a quick inbox mode, something like `/fodo:add --quick <text>` (or capturing several items
at once) that only writes the request text. Clarifying it then happens during `plan` or `review`.

## Analysis
GTD's Capture step should take no effort; today `/fodo:add` always researches the code to size and
plan the item. A quick mode writes only frontmatter (type guessed from the text, `size: unknown`)
plus `## Request`, and skips the code research. Multi-capture: several lines (or a pasted list)
become several items in one call. `/fodo:plan` and the planned review item must handle items with
empty Analysis/Plan sections. Check that `fodo.sh` and the dashboard tolerate `size: unknown`.

## Impacted files
- `plugins/fodo/skills/add/SKILL.md`: `--quick` flag, automatic quick mode for several lines, keyword type guess
- `plugins/fodo/reference/item_template.md`: minimal "quick item" variant
- `plugins/fodo/skills/plan/SKILL.md`: fill in a quick item's missing sections and size; may correct its type once via `fodo.sh retype`
- `plugins/fodo/skills/start/SKILL.md`: on a quick item, fill in first (as add does), suggest plan if medium/large
- `plugins/fodo/reference/conventions.md`: quick items + the one exception to "filenames are immutable"
- `plugins/fodo/scripts/fodo.sh`: new `retype <file> <bug|change|feature>` command (quick items only)
- `tests/fodo.bats`: retype tests; `size: unknown` lists fine
- `plugins/fodo/README.md`: `/fodo:add` row documents `--quick` and lists

## Plan
See `### Implementation blueprint` in the PRP below (Tasks 1–8).

## Acceptance criteria
- `/fodo:add --quick a\nb\nc` creates three minimal items without reading the codebase
- Quick items list and render normally, with size shown as unknown
- `/fodo:plan <n>` on a quick item fills in analysis, size, plan and criteria

## PRP

### Goal
`/fodo:add --quick <text>` captures an item in seconds: no code research, only frontmatter (`size: unknown`, type
guessed from keywords) and the `## Request` section. Giving `/fodo:add` several lines or a bullet list always captures
quickly, one item per line. Quick items list and render normally, with size "unknown". `/fodo:plan <n>` and
`/fodo:start <n>` fill in the missing sections before doing their own work. Plan may correct a wrongly guessed type
once, through a new helper command `fodo.sh retype`.

### Why
- GTD's capture step should take no effort. Today every `/fodo:add` researches the codebase, which is slow when jotting down several ideas.
- Clarifying moves to the moment the item is picked up (plan/start, later the planned `/fodo:review`).
- It keeps the archive intact: quick items are real items in `docs/todo/`, with stable filenames.

### Decisions taken
- Invocation → **`--quick` flag, plus automatic quick mode when the text has several lines or a bullet list** (one
  item per non-empty line, list markers `-`, `*`, `1.` stripped). Plain-language "jot these down: …" maps to it. No new skill. (user)
- Type → **keyword guess at capture; `/fodo:plan` may correct it once** with `fodo.sh retype`, the single exception to
  "filenames are immutable", allowed only while `size: unknown`. Keywords: bug if the text says broken, bug, error,
  fails, crash, wrong, doesn't/does not work; feature if it says add, new, support, allow, introduce; otherwise change. (user)
- `/fodo:start` on a quick item → **fill in first** (type check, size, Analysis, Impacted files, Plan, Acceptance
  criteria, exactly as add's steps 1–4 research). If it comes out medium/large, suggest `/fodo:plan <n>` and stop before
  moving to busy. Small: continue with start as usual. Start never retypes; only plan does. (user)
- Marker → **`size: unknown`** is what makes an item "quick". No extra field. Plan/start replace it with the real size. (user)
- Retype is a **helper command**, not a bare `git mv` in skill text, because conventions say all moves go through the
  helper. It refuses unless the item has `size: unknown`, so it can't rename sized items. (default, Claude)
- Two-minute rule (add step 6) → no change. Its "offer depends on the sizing in step 2" sentence already excludes quick items. (default, Claude)
- `/fodo:review` (planned item "Add /fodo:review weekly review command") → not built here. Its future skill should treat `size: unknown` as "needs clarifying". (default, Claude)

### Known gotchas & library quirks
- `retype` must refuse: an unknown type (only bug|change|feature), a file without `size: unknown` ("only quick items
  can be retyped"), the same type (no-op message, exit 0), and a target filename that already exists.
- New filename: replace only the 2nd dot-field. `new="${base%%.*}.$type.${base#*.*.}"` (date.type.slug.md → date.NEW.slug.md).
- After renaming, update `.current` if it held the old basename (retype in busy shouldn't happen, but be safe), and reindex.
- Also set frontmatter `type:` to the new type (`set_field`), since the template has it.
- `set -euo pipefail` is on in fodo.sh: guard greps with `|| true` where no match is expected.
- Shellcheck must stay clean. Quote everything.
- Quick capture must not read the codebase at all: no grep/read of source files. Slug and title come from the text only.
- Multi-line capture: also apply step 5's duplicate check (same title as an existing planned item → append the request instead).
- IDs shift after each new item. After a multi-capture, reindex once and show the list of new IDs + titles.
- bats here is 0.4.0 (no `-f`). Run the whole file.

### Anti-patterns
- Don't research the codebase in quick mode. That defeats the purpose.
- Don't rename files from skill text with `git mv`. Only `fodo.sh retype` renames, and only quick items.
- Don't change full-mode add behaviour (steps 1–6) or the two-minute rule.
- Don't add a new status or folder (no `inbox/`). Quick items are ordinary planned items.
- Don't let start retype or turn a medium/large quick item into busy without a plan.
