# Investigate ICM as a docs/ convention and as a Claude plugin

## Request
investigate if Interpretable Context Methodology (ICM) https://github.com/RinDig/Interpretable-Context-Methodology could be an idea that
- fits the docs/ subfolder for a repo's documentation
- would make for a good Claude Plugin

## Analysis
This is a research spike, not code: the deliverable is a written go/no-go with reasons, and possibly
a follow-up item (or a new plugin skeleton) if the answer is yes.

What ICM is (from the repo README, 2026-10-30): "folder structure as agent architecture". A single
agent walks numbered stage folders; markdown files tell it what role to play at each step.

- Layer 0 `CLAUDE.md` (always loaded, "where am I"), layer 1 root `CONTEXT.md` (task routing),
  layer 2 `stages/NN-name/CONTEXT.md` (stage contract: Inputs / Process / Outputs),
  layer 3 `references/`, `_config/`, `shared/`, `skills/`, layer 4 `stages/NN-name/output/`.
- Conventions in `_core/CONVENTIONS.md` (15 patterns): CONTEXT.md under 80 lines, reference files
  under 200 lines, stage outputs never committed. A typical stage loads 2k to 8k tokens.
- Designed for Claude Code: `cd workspaces/<name>`, type `setup`, answer `setup/questionnaire.md`,
  then step through the stages. `workspaces/workspace-builder` generates new workspaces.
- Stated limits: sequential, human-reviewed, repeatable workflows only; not for concurrent or
  heavily branching work.

Question 1, fit for `docs/`: ICM is a *workflow* structure (stages with inputs and outputs), while
`docs/` in this repo and in most repos is *reference* documentation (`docs/index.md`,
`docs/publishing.md`, `docs/todo/`). The layer-3 pieces (`references/`, `shared/`, CONVENTIONS-style
limits on file length) map well onto `docs/`; the numbered `stages/` and `output/` folders do not,
and would collide with the existing `docs/todo/` lifecycle that fodo already owns. Compare with the
`mkdokf` skill already installed here (OKF knowledge base under `docs/agents/`), which is a closer
fit for "documentation for agents" and would be the thing ICM competes with.

Question 2, as a Claude plugin: plausible. A plugin could ship skills like `/icm:init` (scaffold a
workspace from the questionnaire), `/icm:stage <n>` (run one stage, honouring checkpoints and
audits), `/icm:status` (which stage has output, which is next) and `/icm:lint` (the CONVENTIONS
checks: line limits, no committed outputs). The marketplace already has the layout for a second
plugin. Open questions: licence of the ICM repo and whether its author wants a plugin; whether the
plugin should own the folder convention or only drive an existing ICM workspace; overlap with fodo
(both put agent state in markdown folders), and whether `stages/NN/output/` handoff is better served
by fodo's done/ items.

Risks: scope creep into building the plugin before the go/no-go is written; the ICM repo is young
and its conventions may still move.

## Impacted files
- `docs/todo/decisions/<date>.icm-go-no-go.md`: the outcome recorded with `fodo.sh decide`.
- `.claude-plugin/marketplace.json`: only if a second plugin is created.
- `plugins/<icm>/`: only if go; new plugin with `.claude-plugin/plugin.json`, skills and reference.
- `docs/index.md`: only if ICM-style layering is adopted for this repo's own docs.

## Plan
See the PRP below (Approach and Validation loop). In short: hands-on run of the ICM
workspace-builder, write `docs/research/icm.md`, record the decision, file follow-ups on a go.

## Acceptance criteria
- `docs/research/icm.md` exists, renders in mkdocs, and answers both questions with reasons and a
  comparison table (ICM vs this repo's docs/ vs mkdokf `docs/agents/` vs fodo `docs/todo/`).
- It contains evidence from an actual run (setup + at least two stages), not only a reading.
- A decision record exists in `docs/todo/decisions/` with the go/no-go for each question.
- If go for the plugin: a follow-up planned item exists with the skill list and a size estimate.
- No plugin code is written as part of this item; no ICM files are copied into this repo.

## PRP

### Goal
A published research page `docs/research/icm.md` and a decision record that answer, with evidence
from a real run: (1) does ICM's layered folder convention belong in a repo's `docs/`, for any repo
with this repo as the test case; (2) is a standalone `icm` plugin in this marketplace worth building,
and if so what it would contain. On a go, one follow-up planned item exists for the plugin skeleton.

### Why
- Peter wants to know whether ICM is an idea worth adopting or shipping before any code is written.
- This marketplace (`.claude-plugin/marketplace.json`) has one plugin, fodo. A second one must have a
  clear boundary with fodo, which also keeps agent state as markdown folders.
- The write-up outlives the todo item; the decision record makes the verdict findable from fodo.

### Decisions taken
- Depth of investigation → hands-on: clone ICM, run `setup` and at least two workspace-builder stages

- Where the hands-on run lives → in the scratchpad, never inside this repo; nothing from ICM is copied

### Known gotchas & guardrails
- Do the hands-on run in the scratchpad clone (`git clone --depth 1`), in a separate Claude Code
  session started inside `workspaces/workspace-builder/`, because ICM relies on that folder's
  CLAUDE.md being the auto-loaded one. Running it from this repo would load this repo's context.
- PRESERVE: nothing from the ICM repo is copied into this repo; link to GitHub URLs instead.
- Keep the ICM licence (MIT, "Model Workspace Protocol Contributors") in the write-up; it decides
  whether a plugin may embed its templates.
- The write-up must keep the two questions separate; "fits docs/" is about reference documentation,
  which is only ICM Layer 3. Say explicitly what happens to Layers 1, 2 and 4 in a docs/ folder.
- fodo already owns `docs/todo/` and mkdokf `docs/agents/`; any docs/ proposal must name the folder
  ICM would take and must not collide with those two.
- Decisions are created with `fodo.sh decide "<title>" --item <this file> --by start`, never by
  hand (conventions.md). Follow-up items go through `/fodo:add`, not by writing files directly.
- Markdown style of this repo: no em dashes, tables for comparisons, headings max h3 on docs pages.

### Approach
Clone ICM into the scratchpad and read `_core/CONVENTIONS.md` plus the workspace-builder workspace.
Run it hands-on in its own Claude Code session: `setup` with a small invented domain (for example
"blog post to newsletter"), then stages 01-discovery and 02-mapping, noting the questions asked,
tokens loaded per stage, where it stalls and how editable the outputs are. Then write
`docs/research/icm.md` with: what ICM is in one paragraph, the hands-on log, a comparison table with
four columns (ICM, this repo's docs/, mkdokf docs/agents/, fodo docs/todo/) over rows such as
purpose, unit of structure, lifecycle, who edits, token discipline, entry point; a verdict section
per question; and, for the plugin, a proposed skill list (`/icm:init`, `/icm:setup`, `/icm:stage`,
`/icm:status`, `/icm:lint`), what it owns versus what stays in the user's workspace, and a size
estimate. Record the verdict with `fodo.sh decide` and, on a go, add the follow-up item with
`/fodo:add`. Finish with `/fodo:done`.

```bash

# Manual: on a plugin "go", `fodo.sh list` shows a new planned item for the icm plugin skeleton;
#         no file under plugins/ was added or changed (git status --short plugins/ is empty).
```
