# Add a /fodo:changelog skill that creates or updates CHANGELOG.md (Keep a Changelog)

## Request
add skill fodo:changelog that create a CHANGELOG.md file is it doesn't exist yet, writes/updates one from git log or git status, asks questions about what info to include - cf https://keepachangelog.com/en/1.1.0/

## Analysis
Net-new skill; nothing in fodo writes a changelog today and this repo has no CHANGELOG.md itself
(57 commits, tags `v0.1.7` to `v0.1.9` exist, `VERSION.md` holds `0.1.14`, `bin/release.sh` bumps
VERSION.md and every `plugins/*/.claude-plugin/plugin.json`, commits, tags and pushes).

Shape, as a prompt-only SKILL.md like `skills/show/SKILL.md` plus a reference file like
`reference/conventions.md`, so the Keep a Changelog rules are not repeated in the prompt:

- **Create mode** (no `CHANGELOG.md` at the repo root): write the Keep a Changelog 1.1.0 skeleton
  (title, intro sentence, `## [Unreleased]`, one `## [x.y.z] - yyyy-mm-dd` per existing tag when
  the user wants history back-filled, comparison links at the bottom when a remote exists).
- **Update mode** (file exists): read it, find the last version heading, take `git log
  <last-tag-or-heading>..HEAD` (released range) and, if asked, `git status` / `git diff` for
  uncommitted work, and sort the entries into the six Keep a Changelog groups: Added, Changed,
  Deprecated, Removed, Fixed, Security. Conventional-commit prefixes map directly
  (`feat` → Added, `fix` → Fixed, `chore`/`docs`/`refactor` → usually dropped or Changed);
  otherwise the skill reads the diff.
- **Questions** (AskUserQuestion, few rounds): back-fill history or start from now; include
  docs/todo bookkeeping and chores or only user-visible changes; date and version for a new
  release section or leave it under Unreleased; whether a fodo `done/` item should be the source
  for an entry's wording (done items have a Result section and a title, often better than commit
  subjects).
- Never commits; `/fodo:commit` (planned item, `2026-10-30.feature.fodo-commit-skill.md`) is the
  one that asks about CHANGELOG.md before committing, so the two skills should agree on the
  file format and `/fodo:commit` can delegate to this skill's rules.

Open questions for `/fodo:plan`:
- Should `bin/release.sh` promote `## [Unreleased]` to `## [<new>] - <date>` when it bumps the
  version? That makes the changelog part of the release, but adds a shell edit to a prompt skill.
- Source priority when both exist: fodo `done/` items vs git commits for the same change.
- Does the plugin's own `plugins/fodo/CHANGELOG.md` make more sense than a root one for a
  marketplace repo with several plugins? (The plugin directory shows per-plugin metadata.)
- Does the skill belong in fodo at all, or in a separate small plugin, since it is not about
  todos? Fodo already owns decisions and gotchas, so "project memory in markdown" is a fit.

Risks: rewriting an existing hand-written changelog; mitigate by only inserting under Unreleased
or a new version heading and never reordering or deleting existing entries.

## Impacted files
- `plugins/fodo/skills/changelog/SKILL.md`: the new skill, create and update modes, the questions.
- `plugins/fodo/reference/changelog.md`: the format reference (sections, heading forms, link
  footer, mapping from commit prefixes and from fodo item types bug/change/feature).
- `plugins/fodo/README.md`: Commands table row and a sentence in the overview.
- `plugins/fodo/.claude-plugin/plugin.json`: add `changelog` keyword, optional.
- `bin/release.sh`: optional Unreleased → version promotion.

## Plan
See the PRP below (Approach and Validation loop).

## Acceptance criteria
- In a repo without `CHANGELOG.md`, `/fodo:changelog` creates a valid Keep a Changelog 1.1.0 file
  with an `[Unreleased]` section and, when asked, one section per existing tag.
- In a repo with one, it adds entries under `[Unreleased]` or a new version heading from the
  commits since the last version, grouped into the six standard categories, and never removes or
  reorders existing entries.
- It asks before including chores/bookkeeping and before back-filling history.
- It never runs `git commit` or `git push`.
- README Commands table lists the skill; `bats tests/` passes.

## PRP

### Goal
`/fodo:changelog` exists as a prompt-only skill. In a repo without a root `CHANGELOG.md` it creates a
Keep a Changelog 1.1.0 file (header, intro, `## [Unreleased]`, optional back-filled sections per
existing tag, compare links when the remote is GitHub or GitLab). In a repo with one it inserts the
changes since the last version heading under `## [Unreleased]`, grouped into Added/Changed/
Deprecated/Removed/Fixed/Security, optionally promoting Unreleased to a version heading. Entries come
from the commits in range, with the wording taken from the fodo `done/` items completed in that
range when there are any. It asks few questions, shows the diff, and never commits or pushes.
`/fodo:commit` step 6 and this skill follow the same rules, written once in
`plugins/fodo/reference/changelog.md`.

### Why
- A changelog is the one project-memory file fodo does not write yet; `/fodo:commit` already updates one but refuses to create it, so repos without one never get entries.
- Done items carry better wording than this repo's bundled commits (`chore: commit 17 changed files before release`), so fodo can write a changelog git log alone cannot.
- One reference file keeps `/fodo:commit` and `/fodo:changelog` from drifting on heading forms and group mapping.

### Decisions taken
- Where does the file live in a multi-plugin repo? → root `CHANGELOG.md` only, the file `/fodo:commit` already updates (user) (recorded: decisions/2026-11-06.the-changelog-is-the-root-changelog.md)
- Entry sources? → commits since the last version are the skeleton; when `docs/todo/done/` items have a `done_at` inside the range, their title and Result wording replace the commit subject; uncommitted work is offered as a question, never read by default (user) (recorded: decisions/2026-11-06.changelog-entries-come-from-commits-since.md)
- Should `bin/release.sh` promote Unreleased on a bump? → no; `/fodo:commit` already does, and decision D33 keeps release.sh as the no-fodo path (user)
- Arguments? → none; everything is asked with AskUserQuestion, at most two rounds (user)
- Which commits are dropped without asking? → `release: set version to …`, `chore: commit N changed files before release`, merge commits, and commits that only touch `docs/todo/**` or `CHANGELOG.md` (default, mirrors `/fodo:commit`'s "bookkeeping" rule)
- Which commits are asked about? → `chore`, `docs`, `refactor`, `test`, `ci`, `build` as one yes/no "include housekeeping?"; `feat`, `fix`, `perf`, `!`/BREAKING always in (default)
- Range detection? → last `## [x.y.z]` heading in the file, else the highest `v?x.y.z` tag (`semver.sh current` logic), else the whole history (default)
- Compare links? → footer `[Unreleased]: <remote>/compare/v<last>...HEAD` and `[x.y.z]: <remote>/compare/v<prev>...v<x.y.z>` only when `git remote get-url origin` is github.com or gitlab.com and the tags exist; otherwise no footer (default)

### Known gotchas & guardrails
- Mirror the existing patterns named under Context; do not introduce new ones for this item
- PRESERVE: existing CHANGELOG.md lines are never reordered, rewritten or deleted; the skill only inserts lines under `## [Unreleased]` (creating the section and the group headings it needs) or promotes that heading to a version. Hand-written entries that already describe a commit in range are kept and the commit skipped (match on the commit subject or the done item title)
- PRESERVE: `/fodo:commit` step 6 behaviour (entry form `- <subject without prefix>`, group mapping, promotion on bump). The reference file states these once; step 6 shrinks to a pointer plus the parts specific to commit (the single entry, `git add CHANGELOG.md`)
- CRITICAL: this repo's own history is bundled release commits; the skill must handle a range where every commit is dropped as bookkeeping by falling back to the done/ items in range, and if those are empty too, say "nothing to add" instead of writing an empty group
- CRITICAL: `done_at` is a date, commits have timestamps; "in range" means `done_at` between the date of the range start commit and today, inclusive
- CRITICAL: never run `git commit`, `git push`, `git tag` or `bin/release.sh`; end with "Review the diff; `/fodo:commit` commits it"
- Mapping from done item types when a done item has no matching commit: bug → Fixed, feature → Added, change → Changed
- Back-filling on create: one `## [x.y.z] - <tag date>` per tag, `git log <prev>..<tag>` mapped with the same rules; the back-fill question is the first question and defaults to "Unreleased only" when the repo has more than 20 tags (say why)
- Also update: `plugins/fodo/README.md` (Commands table row after `/fodo:commit`, and a sentence in the "decisions" paragraph that the changelog is the third memory file), root `README.md` Commands table, `plugins/fodo/skills/help/SKILL.md`, `plugins/fodo/dashboard/faq.md`, `assets/cheatsheet.html` + re-rendered PDF, plugin.json description (mention the changelog; keyword `changelog` is already there)
- The SKILL.md frontmatter description starts with `[this repo]` like the other per-repo skills and ends with trigger phrases ("write the changelog", "update CHANGELOG.md", "what changed since the last release")

### Approach
Two new files and a handful of one-line edits. `reference/changelog.md` holds the format (header,
intro, section and group order, heading forms, the footer links), the commit → group mapping, the
done-item → group mapping, the bookkeeping filter and the insertion rules (where Unreleased goes,
how promotion works, never touch existing lines). `skills/changelog/SKILL.md` is the flow: detect
create vs update → find the range (`semver.sh current`, last heading, tags) → collect commits and
done items in range → first AskUserQuestion round (back-fill or not when creating; include
housekeeping commits; include uncommitted changes; promote Unreleased to a version, with
`semver.sh next` candidates, or leave it) → write → `git diff --stat CHANGELOG.md` and the inserted
block in the report. `commit/SKILL.md` step 6 becomes "follow reference/changelog.md" plus its two
commit-specific lines. Then the docs round: help, FAQ, both READMEs, cheatsheet.
