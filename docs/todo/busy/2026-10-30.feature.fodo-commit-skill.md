# Add a /fodo:commit skill that stages, describes, commits and bumps the semver like setver

## Request
an extra fod:commit skill that does: git add . (if new files are detected) - create short descriptive commit message - if CHANGELOG.md exists, should it be updated - commit -a -m "<commit message>"

Added at planning (2026-10-30): when doing commit, also estimate if it's a patch/minor/major version
update and handle semver versioning in the same way setver.sh does

## Analysis
Net-new skill (`fod:commit` in the request is read as `/fodo:commit`). Today no fodo skill touches
git beyond `git mv` in the helper and `git log` in `/fodo:review`; the README, PRIVACY.md and
conventions.md all promise "it never commits or pushes" and "do not commit unless the user asks".
Running `/fodo:commit` *is* the user asking, so the skill is compatible with the rule, but the three
texts must be reworded to say that only this skill commits and nothing ever pushes.

Shape of the skill, as a prompt-only SKILL.md like `skills/show/SKILL.md` (no helper change needed):

1. `git status --porcelain`; stop with a message when the tree is clean.
2. Untracked files present → `git add -A` (the request says `git add .`; `-A` from the repo root
   is the same and also picks up deletions). Respect `.gitignore`; never force-add.
3. Build a short, descriptive subject from `git diff --cached --stat` and the diff itself, in the
   style of this repo's history (`type: summary`, e.g. `feat: add /fodo:commit skill`), with the
   attribution trailer Claude Code is configured to add.
4. CHANGELOG.md: when the file exists at the repo root, decide whether the change deserves an
   entry (user-visible behaviour: yes; typo, refactor, docs/todo bookkeeping: no). If yes, add a
   line under the unreleased/top section before committing so it lands in the same commit; follow
   the file's existing format (Keep a Changelog or otherwise). If unclear, ask with one question.
5. `git commit -a -m "<subject>"` (plus a body when the diff spans several concerns). Never push.
6. Print the resulting `git log -1 --stat`.

Open questions were settled at planning; see `### Decisions taken` in the PRP.

Risks: committing secrets or large files that `.gitignore` misses; mitigated by showing the staged
file list before committing and refusing files over a size threshold or matching `.env*`.

## Plan
See the PRP below (Approach and Validation loop). In short: a `semver.sh` helper for the version
files, a prompt-only `skills/commit/SKILL.md` for message, bump estimate, CHANGELOG and commit, and
the three wording fixes.

## Acceptance criteria
- `/fodo:commit` on a clean tree prints "nothing to commit" and changes nothing.
- With untracked and modified files it stages them, proposes a short conventional-commit style
  message (or uses the given `<message>`), proposes a bump (patch, minor, major or none) with the
  reason, asks once, and creates exactly one commit; `git status` is clean afterwards.
- A confirmed bump writes the new version into every version file present (setver's set plus
  `.claude-plugin/plugin.json` files), includes them in the same commit and creates tag `v<x.y.z>`.
- Nothing is ever pushed, and no file is force-added.
- With a root `CHANGELOG.md` it adds the entry under `[Unreleased]`, or under a new
  `## [x.y.z] - <date>` section when a bump was confirmed, in the same commit.
- `semver.sh` has bats tests for current-version detection, bump arithmetic and each file type.
- README Commands table lists the skill; PRIVACY.md and conventions.md no longer claim fodo never
  commits, but still say it never pushes.
- `shellcheck plugins/fodo/scripts/*.sh` and `bats tests/` pass.

## PRP

### Goal
`/fodo:commit [<message>]` turns the working tree into one well-described commit: it stages new
files, writes (or takes) the subject, estimates the semver impact from the diff, asks once to
confirm the bump, writes the version into every version file the repo has, updates CHANGELOG.md
when present, commits, and tags `v<x.y.z>` when a bump happened. It never pushes. The version-file
logic lives in a new tested helper `plugins/fodo/scripts/semver.sh`.

### Why
- Peter commits with `setver auto` / `setver new` in most repos; inside Claude Code the same flow
  should be one skill, with a better commit message than setver's `MOD: a.md b.sh` list.
- This repo's `bin/release.sh` bumps VERSION.md and plugin.json together at release time; a
  per-commit bump that knows plugin.json keeps `tests/release.bats` ("VERSION.md matches every
  plugin.json") green and lets release.sh become mostly "check, tag if needed, push".
- The planned `/fodo:changelog` item (docs/todo/2026-10-30.feature.fodo-changelog-skill.md) needs a
  commit step that respects Keep a Changelog; this skill is that step.

### Decisions taken
- Bump mode → estimate from the staged diff and commit type, show the proposal and reason, confirm
  with one AskUserQuestion that also offers "no bump", then write version files in the same commit (user) (recorded: decisions/2026-10-30.fodo-commit-estimates-the-semver-bump.md)
- Tag and push → create tag `v<x.y.z>` locally after a confirmed bump; never push, the user pushes
  with `git push --follow-tags` or `bin/release.sh` (user) (recorded: decisions/2026-10-30.fodo-commit-tags-v-x-y.md)
- Version files → inline, setver's set plus Claude plugin manifests: VERSION.md, composer.json
  (`"version"` field, via `composer config version` when composer exists, else awk), package.json
  (+ package-lock.json, via `npm version --no-git-tag-version` when npm exists, else awk),
  `.env.example` lines `VERSION=` / `APP_VERSION=`, a shell script's `version=` / `VERSION=` line when
  the repo root holds exactly one `*.sh` with such a line, and every `.claude-plugin/plugin.json` and
  `plugins/*/.claude-plugin/plugin.json` top-level `"version"` (user) (recorded: decisions/2026-10-30.fodo-commit-writes-the-version-into.md)
- Arguments → optional `<message>` used as the subject; the bump estimate still runs on the diff with
  the message's `feat`/`fix`/`!` prefix as a hint (user)
- Where the logic lives → a bash helper `scripts/semver.sh` with bats tests does detection, arithmetic
  and file writes; the SKILL.md only reasons about the message and the bump level (default: the
  prompt must not reimplement awk edits, and release.sh's awk for plugin.json is reused verbatim)
- Bump mapping → setver's `suggest_next_version_bump`: `!` or "BREAKING" → major, `feat` → minor,
  `fix` and everything else → patch; plus "none" when only `docs/todo/**`, `*.md` under docs/ or
  CHANGELOG.md changed (default: bookkeeping commits must not bump) (recorded: decisions/2026-10-30.fodo-commit-maps-commit-types-to.md)
- Current version → setver's `get_any_version` order: VERSION.md, then highest `v?x.y.z` git tag
  (`git tag --sort=version:refname`), then composer.json, package.json, shell script; `0.0.0` when
  none (default)
- Message style → conventional commits as this repo's history uses them (`feat: …`, `fix: …`,
  `chore: …`, `release: …`), subject ≤ 72 chars, a body only when the diff spans several concerns,
  attribution trailer as Claude Code's session reminder dictates (default)
- CHANGELOG.md → when it exists: no bump → add the entry under `## [Unreleased]` in the matching Keep
  a Changelog group (feat → Added, fix → Fixed, else Changed); bump → rename `## [Unreleased]` to
  `## [x.y.z] - <today>`, add the entry there and insert a fresh empty `## [Unreleased]` above. Never
  reorder or delete existing lines. No CHANGELOG.md → do not create one (that is `/fodo:changelog`'s
  job) (default) (recorded: decisions/2026-10-30.fodo-commit-updates-an-existing-changelog.md)
- Safety → show the staged file list before committing; refuse to continue when a staged file matches
  `.env`, `*.pem`, `*.key`, `id_rsa*` or is larger than 5 MB, and say which (default)

### Known gotchas & guardrails
- Mirror the existing patterns named under Context; do not introduce new ones for this item.
- CRITICAL: never run `git push`, `git push --tags` or `git add -f`. `git add -A` from the repo root
  only, after showing `git status --short`.
- CRITICAL: `release.sh` tags and pushes `main`; `tests/release.bats` asserts VERSION.md equals every
  `plugins/*/.claude-plugin/plugin.json` version. semver.sh must update all of them in one call or
  the next release fails.
- `git tag --sort=version:refname` is needed for the current version; plain `git tag` sorts
  1.10.0 before 1.6.0 (setver comment). Strip an optional `v`.
- plugin.json must keep its formatting: only the `"version"` line changes (release.sh awk). Do not
  pipe it through jq or python json.
- macOS first: BSD `sed -i` needs `''`; prefer writing to `$f.tmp` and `mv` like release.sh.
- The skill is prompt-only for reasoning but every file write goes through `semver.sh set <x.y.z>`
  (prints one line per file it changed, exits 1 when it changed nothing) so the tests cover it.
- `semver.sh next <patch|minor|major> [current]` prints the new version only; `semver.sh current`
  prints the detected version and its source on stderr; `semver.sh tag <x.y.z>` creates an annotated
  tag `v<x.y.z>` and refuses when it exists.
- A bump is proposed as "none" when only bookkeeping changed (see Decisions); the user can still
  pick a level in the question.
- When the tree is clean, say so and stop; do not create an empty commit.
- Also update: README Commands table, README terminal commands table, PRIVACY.md, conventions.md,
  plugin.json description and keywords (`commit`, `semver`, `changelog`), DEVELOP.md test list if it
  enumerates bats files.
- PRESERVE: fodo.sh is untouched; semver.sh is a separate script so `/fodo:cli` keeps linking only
  fodo.sh.

### Approach
New `plugins/fodo/scripts/semver.sh` (commands `current`, `next`, `set`, `tag`) built like fodo.sh
and reusing release.sh's awk for plugin.json; `tests/semver.bats` covers detection order, the
arithmetic (patch/minor/major resets), each file type in a temp repo, the plugin.json formatting
guarantee and the tag refusal. New `plugins/fodo/skills/commit/SKILL.md`: stop on a clean tree;
`git status --short` and stage; run the safety check; read the diff and write the subject (or take
`$ARGUMENTS`); derive the bump level from the subject prefix and the diff with the bookkeeping
exception; one AskUserQuestion "Commit as `<subject>` and bump <current> → <next> (<reason>)?" with
options for the proposed level, the other levels and "no bump"; on a bump run `semver.sh set`;
update CHANGELOG.md per the decision; `git add -A` again for the version and changelog files;
`git commit`; `semver.sh tag` on a bump; print `git log -1 --stat` and the hint to push with
`git push --follow-tags`. Then the wording changes in README, PRIVACY, conventions, plugin.json, and
the one-line comment in release.sh.
